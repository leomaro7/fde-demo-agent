# 手順書は書きながら実行する

**書いてから検証する順序を取らない。** 前身のプロジェクトでは README を全部書いた後に
通し検証し、6 箇所の欠陥が出た。要件書 9.1 はこれを「やらないほうがよいこと」の
筆頭に挙げている。

順序が逆だと、書いている最中の自分は「たぶんこう動くはず」で埋めてしまう。
その推測は、実行するまで推測だと気づけない。

## 主経路：1 手順ずつ

**これが既定の進め方。**

```
手順を 1 つ書く
  → その場で実行する
  → 実際の出力を確認する
  → 出力に合わせて手順を直す（想定と違えば手順のほうが間違い）
  → 次の手順へ
```

**まとめて書いてからまとめて流さない。** 3 つ書いて 3 つ流すと、どの手順が
どのエラーを起こしたのかの対応が崩れ、結局全部やり直しになる。

各手順を書いたら、次を自分に確認する。

| | |
|---|---|
| 実行した | していないなら、それは手順ではなく下書き |
| 出力を見た | 期待どおりか。違うなら手順を直す |
| 2 周目で成立するか | 既にリソースがある状態で、この手順は何を返すか |

### 実行できないものの扱い

ブラウザ操作、外部サービスの認可、課金が発生する操作は実行できないことがある。
そのときは**推測で書かず**、次のどれかを取る。

1. `claude-in-chrome` が使えるなら**実際に画面を開いて確かめる**
2. 使えないならドキュメントを調べ、根拠を添える
3. それも無理なら**「未確認」と明記して人に確認を求める**

前身では Amplify のコンソール操作を画面を見ずに書き、新規アプリ作成時の画面と
既存アプリの画面を取り違えていた。推測で書いた手順は、読者が詰まったときに
「自分が間違えたのか、手順が間違っているのか」の判断すら奪う。

# 既にある手順書を検証する

**他人が書いた手順書、過去に書かれた手順書、大幅に書き換えた手順書**が対象。
主経路を取れなかった場合の後追いなので、ここに来る時点で欠陥がある前提で読む。

## Step 0：読んで分かる欠陥を先に潰す

**実行する前に、読むだけで分かるものを片付ける。** 実行は時間もリソースも使うので、
静的に見つかるものをそこで消費しない。

### 判断できない条件分岐

**最も見落とされやすい。**

```markdown
既に有効なら、このコマンドは実行不要です。
```

**確認する手段が示されていなければ、読者は判断できない。** 実行してエラーを
見るまで分からないという書き方になっている。確認するコマンドが先に来るべき。

同種のパターン: 「必要なら」「まだの場合は」「未設定であれば」。

### 2 周目に壊れる手順

| 例 | 何が起きるか |
|---|---|
| `gh repo create` | 既にリモートがあると失敗する |
| `aws iam create-role` | 同名があると `EntityAlreadyExists` |
| 「〜を作成します」 | 既にある場合の分岐がない |

セットアップ手順は**2 回目に実行されることがある**前提で書かれるべき。

### 変動する数値

テスト件数、ファイル数、所要時間の具体値は古くなる。前身ではテスト件数が
2 箇所にあり、片方だけ直して不整合が起きた。

### 参照の妥当性

- リンク先のファイルが実在するか
- `npm run <script>` が `package.json` に定義されているか
- `file://` パスのファイルが実在するか
- 削除された機能への言及が残っていないか

### 順序の妥当性

手順 N が手順 N+1 の結果に依存していないか。前身では「Amplify に GitHub を接続」が
「GitHub リポジトリを用意」より前にあった。

### 未検証の記述

**コンソール操作は特に疑う。** ボタン名やメニュー階層が具体的に書かれているか、
その画面に本当にその選択肢があるか、「未確認」と明記されているか。

## Step 1：手順を分解する

実行可能な単位に分け、各単位について記録する。

| | |
|---|---|
| 種別 | コマンド / ブラウザ操作 / 判断 / 待機 |
| 前提 | この手順が成立するために必要な状態 |
| 期待結果 | 成功したとき何が起きるか |

## Step 2：前提を素の状態に戻す

可能なら、手順が想定する初期状態を作る。既にリソースがある状態で検証すると、
初回の手順が通るかが分からない。

**素に戻せない場合はその旨を記録して先に進む。** ただし初回の検証にはならない。

## Step 3：一行ずつ実行する

コマンドは**コピーしてそのまま流す**。書き換えたら検証にならない。

**手順に書かれていないことを補完しない。** 「たぶんこれが必要だろう」と補った瞬間、
その欠落が見えなくなる。読者は補完できないという前提で読む。詰まったら、
そこで止めて記録する。それが欠陥である。

失敗したら、次のどれに当たるかを判定する。

| 分類 | 例 |
|---|---|
| **順序が違う** | 先に別の手順が必要だった |
| **前提が書かれていない** | 権限、事前設定、ツールの導入 |
| **コマンドが動かない** | 誤り、環境依存、引数不足 |
| **説明が足りない** | 何をすればいいか分からない |
| **2 周目に壊れる** | 既にリソースがある場合の分岐がない |
| **古い** | 実装が変わったのに手順が追随していない |

## Step 4：手順書を直す

**確認を先、実行を後にする。**

```markdown
まず現在の状態を確認します。

    aws xray get-trace-segment-destination --region ap-northeast-1

"Status": "ACTIVE" と出れば、この手順は飛ばしてください。
```

**想定されるエラーを明記する。** 既に設定済みの場合に出るエラーなど、
「出ても問題ないもの」は先に書いておく。

**変動する数値を書かない。**「失敗が 0 件なら OK」のように書く。

## Step 5：結果を報告する

検証した範囲と、しなかった範囲を明確に分ける。

```markdown
## 検証結果

| 手順 | 結果 |
|---|---|
| 1 依存を入れる | 通過（脆弱性警告の記述を追加） |
| 2 土台を構築 | **未実行**（課金が発生するため要承認） |
| 3 リポジトリ | 対象外（既存のため） |
| 4 Amplify 接続 | **記述を修正**（画面遷移が誤っていた） |

## 直した箇所
...

## 未確認の箇所
- 手順 2: 実行していない。課金が発生するため
```

**「全部確認しました」と書けるのは、全部実行したときだけ。**

## やってはいけないこと

| | 理由 |
|---|---|
| 手順書を全部書いてから検証する | 前身の最大の欠陥。要件書 9.1 が名指しで禁じている |
| 書かれていない操作を補って進む | 欠落が見えなくなる |
| コマンドを書き換えて実行する | 書いてあるコマンドの検証にならない |
| 実行していない手順を「確認済み」と報告する | 最も有害。読者が信じて詰まる |
| 推測でコンソール操作の手順を書き直す | 前身で実際に間違えた |
