# 課題を起票する

**残すのは「何を直すか」ではなく「何がもう分かっているか」。**

やることの説明なら、その場で口頭に出ている。**消えるのは調査の結果のほう**である。
どのコマンドで何が返ったか、何を試して駄目だったか、どこまで確認済みか。
これを書かないと、次のセッションが同じ AWS を建てて同じことを測り直す。

## いつ使うか

- 「次回にしましょう」「後で」「Issue にしておいて」と言われたとき
- 直せるが**今は直さない**と決めたとき
- 調べた結果だけ残して先へ進むとき
- 起票済みの課題に**着手した / 終わった / やめた**とき

## 公開範囲を取り違えない

**土台リポジトリは公開なので、Issue も誰でも読める**（要件書 7.1）。

| | Issue の見え方 | 書いてよいもの |
|---|---|---|
| **土台リポジトリ** | **公開** | 基盤の課題、実測値、AWS の挙動。**架空の見本の話だけ** |
| **企業リポジトリ**（private） | 非公開 | クライアント固有の話 |

**土台リポジトリの Issue にクライアント名や実データを書かない。**
アカウント ID・実リソース ID・ARN・パスワードも同じ。書く前に読み返すこと。

**今どちらにいるかは `git remote -v` で確かめる。**

## 起票する前に

**同じものが無いか見る。**

```bash
gh issue list --limit 30
gh issue list --search "<関係しそうな語>" --state all
```

あれば**新しく作らず、そこにコメントを足す**。分かったことが増えただけなら、それが正しい。

```bash
gh issue comment <番号> --body-file -
```

## 起票する

**本文は標準入力から渡す。** 一時ファイルを作らない（CLAUDE.md）。

```bash
gh issue create --title "<一文で、何をどうしたいか>" --body-file - <<'EOF'
## なぜ今やらないか

<先送りの理由。「時間が無い」ではなく、判断の根拠を書く>

## 分かっていること

**ここが本体。** 実測した値、通ったコマンド、返ってきた文言をそのまま残す。

## 決まっていないこと

<着手する人が最初に決める必要があるもの。選択肢があるなら並べる>

## 触る場所

| ファイル | 何を |
|---|---|

## 終わったと言える条件

<何が確認できたら閉じてよいか。「実装する」ではなく、確かめ方を書く>
EOF
```

**題名は「〜する」で書く。** 「モデル選択の件」では、一覧で見たときに何をするのか分からない。

## 分かっていることの書き方

**次のセッションが再調査しなくて済む粒度で書く。抽象化しない。**

悪い例。

> 呼び出し時にモデルを指定できることを確認した。

良い例。

> `model.bedrockModelConfig.modelId` を本文に入れると効く（`modelId` を直に置いても無視される）。
> 判定は `toolUseId` の接頭辞（Claude は `tooluse_`、GPT は `call_`）。2 回ずつ再現。
> **HTTP 200 は当てにならない。未知のフィールドも 200 で通る。**

**踏んだ落とし穴も書く。** 「これは効かなかった」は、次の人が同じ道を歩かないために要る。

**ドキュメントで確認したのか、投げて確かめたのかを区別する。**
実測しただけのものは、仕様変更で黙って壊れうる。そう書いておく。

## 着手するとき

コメントで知らせる。**GitHub に「着手中」の状態は無いので、コメントが記録になる。**

```bash
gh issue comment <番号> --body "着手。<日付>時点で「分かっていること」が古びていないかを先に確認する。"
```

**AWS の挙動は変わる。** 起票時に測った値は、そのとき通っただけである。

## 終わったとき

**何をしたかではなく、何を確かめたかを書いて閉じる。**

```bash
gh issue close <番号> --comment "<確かめたこと。対応するコミットがあれば短いハッシュも>"
```

やめるときも `--comment` に**やめた理由**を書いて閉じる。消さない。
「なぜこうしなかったのか」を追うときに、判断の途中経過として効く。
