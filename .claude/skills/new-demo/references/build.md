# 作る

**承認が出たらここから。止まらない。**

`RUNBOOK.md` 3.1 と同じ作業をする。手順書は人が読む用、ここは判断込みの手順。
**置き場所やコマンドが食い違ったら `RUNBOOK.md` が正**（そちらが実行して書かれている）。

## 書く順序

**順序を外すと書き直しになる。**

```
1. seed        ← 先に作る
2. tools.ts + tools.test.ts   ← 3 問が引けることをここで確かめる
3. demo.ts     ← 指示文の条件を seed に当てながら書く
4. demos/index.ts に 3 行
```

**なぜこの順序か。**

- **指示文の条件は seed が無いと突き合わせられない。** 条件を先に書くと、
  seed の多数派と逆を言っていることに気づけない（2026-08-12 の事故）
- **3 問が引けないまま指示文を書くと、書き直しになる。** 引けるかはツールと seed で
  決まる。先に確かめる

## 1. seed

`demos/<slug>/seed/*.json`。1 行 1 件で書くと差分が読める。

型ごとの形は [types.md](types.md)。決めた「仕込む傾向」と「意図的な空白」が
本当にそうなっているかを、書き終えてから読み返す。

## 2. tools.ts と tools.test.ts

`demos/<slug>/tools.ts`。近い既存案件を**見本として読む**（コピーしない）。

**一致は AND にする。** OR にすると「会食 立て替え 精算」で「出張の旅費**精算**」が
引っかかり、**答えられない質問に無関係な根拠を付けて答えてしまう。**
これが最も避けたい失敗である。

**戻り値は必ず文字列。** `toolResult.content` は text しか受け付けない（実測）。

**拒む根拠は、返り値の文面として読める形にする。** フラグを持たせても、
文字列に出さなければエージェントは使えない。

### テストに何を書くか

**純粋関数なので TDD の対象**（CLAUDE.md）。ただし目的はカバレッジではなく、
**商談で壊れる箇所を先に潰すこと。** 次の 5 つを必ず入れる。

| 見るもの | なぜ |
|---|---|
| **3 問が、自然な検索語 3〜4 通りで引ける** | エージェントは質問文の語をそのまま渡す。1 通りだけ通しても意味がない |
| **拒む根拠が返り値の文面に出る** | ここが読めるかに、拒めるかがかかっている |
| **意図的な空白が本当に空白** | 「在庫」「原因」などで引けてしまうと山場が消える |
| **拒む条件を過剰適用しない** | 拒まない側の記録も引けること。過剰拒否は回復が難しい |
| **AND になっている** | 無関係な語の組み合わせで空振りすること |

**1 つ目を飛ばさない。** 2026-08-12 に、2 問目「5 万円の備品を買いたいのですが手続きは」
に対し seed は「3 万円を超える経費は事前承認が必要」と書いてあったのに、
**「備品」「購入」という語が seed に無いため引けず、答えられるはずの質問を拒んだ。**
クライアントの前でこれが起きると、デモが機能していないように見える。

引けなかったら、**seed の文面に語を足す**（ツールを緩めるのではなく）。

## 3. demo.ts

指示文は [system-prompt.md](system-prompt.md) を読んでから書く。

`examples` は決めた 3 問。**3 つ目が拒む問い**であることをコメントで残す。
なぜその 3 問なのかは、読み返す人には分からない。

`slug` は英数字とハイフン。`<instance>_<slug>` が 40 文字以内（ハイフンは `_` に変換）。

## 4. `demos/index.ts` に 3 行

**import 2 行と、登録表の 1 行。**

```ts
import { demo as <slug>Demo } from './<slug>/demo.js';      // ← 足す
import { tools as <slug>Tools } from './<slug>/tools.js';   // ← 足す

export const demos: Record<string, DemoEntry> = {
  smoke: { demo: smokeDemo, tools: smokeTools },
  <slug>: { demo: <slug>Demo, tools: <slug>Tools },         // ← 足す
};
```

CDK（`infra/bin/app.ts`）も画面（`web/src/ui/App.tsx`）もこの登録表を見ているので、
**片方だけ直すという事故が起きない。**

土台リポジトリで作った案件は、**見本としての位置づけをコメントに書き足す**
（どの型の見本か）。企業リポジトリなら不要。

## デプロイする前に確認する

**デプロイは 40 秒かかる。手元で分かる誤りをそこで見つけない。**

```bash
npx tsc --noEmit
npm test
npx cdk list -c instance=<instance>
```

| | 見るところ |
|---|---|
| `tsc --noEmit` | 何も出なければ通っている |
| `npm test` | **失敗が 0 件**なら OK。件数は増えるので数えない |
| `cdk list` | 一覧に `FdeDemo-<instance>-<slug>` が出れば、登録表が CDK 側に効いている |

`-c instance=` を忘れると「instance が指定されていません」で止まる。異常ではない。
**`slug` が 40 文字の制限に触れる場合も、ここで落ちる。**

`instance` が分からなければ、既存のスタック名から取る。

```bash
aws cloudformation list-stacks --region ap-northeast-1 \
  --stack-status-filter CREATE_COMPLETE UPDATE_COMPLETE \
  --query 'StackSummaries[?starts_with(StackName, `FdeDemo-`)].StackName' --output text
```

**AWS に何も無い場合でも `cdk list` は通る。** 合成するだけなので、
`instance` は仮の値でよい（登録表が効いているかだけを見ている）。

## スクリプトで自動化しない

**この作業をひな形生成スクリプトにしない。** 要件書 4.3 と 9 章が
テンプレート化を禁じている。型が 4 件ぶんしか見えておらず、
**ひな形を作った瞬間に、次の案件がその型に引きずられる。**

同じ理由で、seed の件数やフィールド名を固定しない。
「近い既存案件を見本として読む」までが上限である。
