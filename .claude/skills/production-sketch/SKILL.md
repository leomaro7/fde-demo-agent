# 本番想定を出す

**商談が止まるのは、デモが刺さった直後。** 「で、本番にするといくらですか」に詰まると、
その場の熱が次回まで持たない。

**ただし構成は聞かないと固まらない。** 決め打ちの構成図を出すと、外れたときに
作り直しになる。**出すのは「推奨構成」と「それを確定させるための問い」の 2 つ。**

**先に読むもの:** [docs/harness-overview.md](../../../docs/harness-overview.md)。
Harness / Gateway / `inline_function` が何を指すか、デモが何で動いているかはそこにある。
**この skill はそれらを説明しない。**

## いつ使うか

- デモを見せた後、本番の話になったとき
- 提案書を書く前に、構成と概算の骨子が要るとき
- 「概算だけ先に」と言われたとき

**デモを作る前には使わない。** `new-demo` に混ぜないこと。打ち合わせメモには
利用規模も既存システムもデータの所在も書かれておらず、**その状態で構成を描くと推測になる**。
本番の問いは、クライアントがデモのどこに食いついたかを見てからのほうが精度が出る。

**4 つ。それ以上は商談の場で読まれない。** HTML 1 枚にこの順で入れる。

| | 中身 |

## 置き場所と公開範囲

**ここを間違えると公開事故になる。着手前に確認すること。**

成果物には**クライアント名・利用規模・既存システム・費用**が入る。全部クライアント固有である。

| | どこに置くか |
|---|---|
| **実クライアントの案件** | **企業リポジトリ（private）のみ**。`demos/<slug>/production-sketch.html` |
| **架空の見本** | 土台リポジトリでよい |

`<slug>` は案件の識別子で、`demos/<slug>/demo.ts` の `slug` フィールドと同じ値。
`new-demo` が案件を作るときに決めている。分からなければ `ls demos/` で確認する。

### Artifact に公開してよいのは架空の見本だけ

**Artifact は claude.ai 上のページで、リポジトリの外に出る。**
既定では非公開だが、**置き場所としては外部ホスティングである**。

- **架空の見本** — 公開してよい
- **実クライアントの案件** — **必ず本人に確認してから。** 勝手に公開しない。
  NDA の範囲は案件ごとに違う

確認せずに出せるのは、**HTML ファイルをローカルのブラウザで開いて見せる**方法。
商談の場ではこれで足りることが多い。**画面共有するだけなら URL は要らない。**

## 1. 聞くことを決める

**構成より先にこれを書く。** 聞かないと決まらないものを先に洗い出さないと、
推測で構成を埋めてしまう。

**効き方が大きい順に並べる。** 商談の場では 2〜3 問しか聞けないことがある。

見本で残った 5 問。**この形は案件が変わっても効く**が、文言は案件に合わせる。
デモで実際に見せた画面と、クライアントが食いついた場面を材料にすると具体的になる。

| 聞くこと | 何が決まるか |
|---|---|
| **データはどこにあり、誰が更新しているか** | 連携方式と工期。**紙なら電子化が別途要る** |
| **月に何件、何人が使うか** | 費用のほぼ全部。従量のままか予約枠か |
| **社内からだけか、外からも使うか** | VPC の要否、通信経路 |
| **ログインは既存の何を使うか** | ID 連携の作り込みと運用負荷 |
| **誤りに誰がどう気づくか** | ログ保持、確認の導線 |

### メモに書かれない 1 点

**「そのデータを、これから誰が書き続けますか」**

`new-demo` の「答えてはいけないこと」と同じ位置にある問い。**打ち合わせでは絶対に出ない。**
クライアントは「AI を入れたい」話をしており、「元データを書き続ける人」の話はしない。

デモは元データが揃っている前提で動く。**実際は、更新が止まった時点で静かに使われなくなる。**
半年後に「最近あたらない」と言われる原因のほとんどがここ。

## 2. 構成を決める

**デモからの差分で書く。** クライアントの頭には「今見たもの」があるので、
ゼロから説明するより速く伝わる。

### どの案件でも変わる 1 点

**ツールの置き場所。** デモはツールもデータもブラウザの中にある（`inline_function`）。
実データはブラウザに配れないので、**Gateway の背後かサーバ側に移る**。ここが最大の変更点。

裏返すと、**Harness とモデルの部分はデモのまま本番で使える。** これは強い材料になる。

### 足さない行を必ず 1 つ入れる

**「変更しません」と書く行を作る。** 全部を作り替える提案は、費用も納期も理由なく膨らむ。

見本では検索方式がそれだった（キーワード一致で足りるなら、ベクトル検索は要らない）。
**何が要らないかを言えると、要ると言ったものの説得力が上がる。**

## 3. 金額を引く

**推測しない。** 引けたものと引けなかったものを分けて書く。

単価は [references/pricing-tokyo.md](references/pricing-tokyo.md) に実測値がある。
**日付を見て、古ければ引き直す。**

### 「1 件」の定義を先に固定する

**1 件 = 利用者が 1 回質問して 1 回答えを得るまで。** 画面での 1 往復。

**その中でモデルは複数回呼ばれる。** ツールを 1 回使えば 2 回（ツールを呼ぶ判断 →
結果を読んで回答）。2 回使えば 3 回。**ここを 1 回で数えると総額が半分になる。**

そして**入力トークンは呼び出しのたびに積み上がる**。2 回目の入力には 1 回目の
やり取り全部が会話履歴として入る。だから概算はこうなる。

```
月間入力トークン  = 件数 × (指示文 + ツール定義 + 質問) × モデル呼び出し回数
                    ＋ 件数 × ツールが返したデータ量
月間出力トークン  = 件数 × 各呼び出しの出力の合計
費用 = 入力 ÷ 1,000,000 × 入力単価 ＋ 出力 ÷ 1,000,000 × 出力単価
```

### トークン量をどう得るか

**デモが動いているなら実測する。** `web/` の画面にトレースが出るので、
1 問投げれば実際の入力・出力トークンが見える。**3 問とも測って平均を取る。**

動いていないときは文字数から概算する。`demos/<slug>/demo.ts` の `systemPrompt` と、
`seed/` のデータ 1 件あたりの文字数、想定ヒット件数を数える。
**日本語はおおよそ 1 文字 1 トークン弱**として見る。

**概算で出したなら「多めに見た値」と資料に書く。** 実測と区別が付くようにする。

### 引き方

**MCP の `call_aws` は使わない。** スペースを含むフィルタ値でクォートが剥がれて弾かれる
（`Value=Claude Sonnet 4.5` が `Sonnet` で切れる）。**ローカルの `aws` CLI を使う。**
作業ディレクトリはどこでもよい。

```bash
aws pricing get-products --service-code <サービスコード> \
  --filters "Type=TERM_MATCH,Field=usagetype,Value=<usagetype>" \
  --region us-east-1 --output json | grep -o 'description[^,]*'
```

`--region us-east-1` は固定（Pricing API の置き場所であって、調べる対象の
リージョンではない）。東京の値は usagetype の `APN1-` 接頭辞で引く。

**usagetype が分からないとき**は先に一覧を出す。

```bash
aws pricing get-attribute-values --service-code <サービスコード> \
  --attribute-name usagetype --region us-east-1 --output text | grep APN1
```

**サービスコード自体が分からないとき**（VPC や NAT Gateway など、
`pricing-tokyo.md` に載っていないもの）は一覧から探す。

```bash
aws pricing describe-services --region us-east-1 --output text | grep -i <サービス名>
```

見つからないときは、そのサービスの料金ページを読む。**推測で単価を書かない。**

### モデル利用料だけは引けない

**確認済み（2026-08-17）。API からは取れない。**
経緯と試した 5 経路は `pricing-tokyo.md` にある。

**人が料金ページを見て転記する。** そこだけは自動化しない。

<https://aws.amazon.com/bedrock/pricing/> を開き、プロバイダのタブを選び、
リージョンを切り替える。**`jp.` プロファイルを使っているなら
「Geo and In-region」の表**を見る（「Global」ではない）。

引けないまま出すときは**オレゴンの実測値で計算し、「オレゴン単価・東京は未確認」と
明記する**（`pricing-tokyo.md` に値がある）。

### 積む順序を間違えない

**費用の 9 割はモデル利用料。** 見本の実測では、月 500 件の想定で
モデル 23.10 ドルに対し、それ以外の合計は 2.61 ドルだった。

**だから他は概算で足りる。** 時間をかけるのはモデル側の前提——
**問い合わせ件数と、1 回あたりに読ませるデータ量**。この 2 つで総額が決まる。

前提は必ず書く。**利用者数・月間件数・1 件あたりのトークン量・応答時間。**
これを書かずに「月◯ドル」と出すと約束になる。
