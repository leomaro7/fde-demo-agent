# リポジトリと Cognito の分割単位 — 設計

作成日: 2026-08-13
対象: 要件書 7.1「リポジトリと Cognito の分割単位」

---

# 1. 結論

**クライアント企業ごとにリポジトリを分ける。土台を共有する仕組みは作らない。**

```
fde-demo-agent（土台リポジトリ）
 └ 案件の見本を型ごとに置く
        │
        │ 新しい企業の話が来たら、ここからコピーして作る
        ▼
企業 A リポジトリ            企業 B リポジトリ
 ├ demos/案件1               └ demos/案件3
 └ demos/案件2
```

| 論点 | 決めたこと |
|---|---|
| リポジトリの分割単位 | **クライアント企業ごと** |
| Cognito User Pool の分割単位 | **クライアント企業ごと**（`instance` を企業ごとに変える） |
| 案件の管理単位 | **同一リポジトリ内の `demos/<slug>/`**。Git のブランチは使わない |
| 土台の共有 | **仕組みを作らない。** その時点の土台からコピーして作る |
| 引き渡す範囲 | **案件部分だけ。** 土台は当社の資産として保持する |

**コードの変更はない。** `instance` で土台を分ける仕組みは既にあり、実測済み。

---

# 2. なぜこうしたか

## 2.1 分割する理由は 1 つに絞られていた

7.1 が書かれた時点では分割の理由が 3 つ挙がっていたが、**2 つは消えた。**

| 当初の理由 | 現状 |
|---|---|
| 他社の案件が入ったリポジトリは渡せない | **残っている。これが分割の理由** |
| 1 リポジトリだと配信物に他社データが混ざる | **2026-08-12 に技術的に解決した**（`vite.config.ts` が `VITE_DEMO_SLUG` から案件を別名解決する） |
| 完全消去には Git 履歴ごと消すしかない | 分割すれば履歴も分かれるので、これは分割の帰結として解決する |

同様に、**現行を後押ししていた論拠も 1 つ消えた。**

「Amplify は 1 アプリ = 1 リポジトリのため、企業ごとに初期設定が要る」——
**Amplify にリポジトリを接続しないと決めた**ため（設計書 2026-08-08 の 4.1）、
この負担は発生しない。

## 2.2 土台を共有する仕組みは作らない

7.1 は「分割する場合の設計課題」として **土台をコピーせず共有する方法**
（npm パッケージ化、テンプレートリポジトリ + subtree など）を挙げていた。

**これを作らないと決めた。**

デモは数週間で廃棄する前提であり、土台に修正が入ったら
**次に作る企業リポジトリから効けば足りる**。既にある企業リポジトリに配る必要が出たら、
その企業のリポジトリで直すか、作り直す。

npm パッケージ化や subtree の運用は、**速度を目的とするこの基盤にとってブレーキ**である
（CLAUDE.md「ブレーキばかり増やすと目的から遠ざかる」）。

**捨てたもの** — 土台の修正が全案件に一度で効くこと。
2026-08-12 に、この利点が実際に効いた場面があった（案件 3 件目で見つけた
「配信物に他案件が混ざる」欠陥の修正が、`main` へのマージだけで全案件に及んだ）。
**分割後はこれが効かない。** 同じ欠陥を別の企業リポジトリでも踏む。

## 2.3 案件のブランチは使わない

7.1 は現行を「1 リポジトリ・1 User Pool・**案件ごとにブランチ**とグループ」と
書いていたが、**ブランチは使っていない。**

2026-08-12 に `demos/index.ts` の登録表と `VITE_DEMO_SLUG` を入れ、
1 つの `main` から全案件を配信できるようにした。
**要件書 6 章の「案件ごとのブランチにクライアント固有の情報が入る」も実態と違う。**

なお Amplify のブランチ（`smoke` / `sales` / `hr`）は案件ごとに存在するが、
これは**配信先の名前であって Git のブランチではない**。リポジトリを接続していないため
Git とは無関係。

# 3. 構成

## 3.1 何が共有で、何が企業固有か

```
土台（企業リポジトリにコピーされる）      企業固有（企業リポジトリで作る）
─────────────────────────────────────    ──────────────────────────────
infra/lib/        CDK の定義              demos/<slug>/demo.ts
web/src/agent/    ハーネス通信            demos/<slug>/seed/
web/src/auth/     ログイン                demos/<slug>/tools.ts
web/src/ui/       画面                    demos/index.ts の登録表の中身
scripts/          配信・実測              instance の値
.claude/          スキルとルール
docs/             要件書・設計・判断
RUNBOOK.md        手順書
```

**企業固有は `demos/<slug>/` と登録表の 1 行だけ。**
2026-08-12 の登録表化で、案件がここに閉じた。

## 3.2 AWS の構成

```
企業 A                                企業 B
 土台スタック（instance=<A社>）         土台スタック（instance=<B社>）
  ├ Cognito User Pool                   ├ Cognito User Pool
  ├ Cognito Hosted UI ドメイン           ├ Cognito Hosted UI ドメイン
  ├ Amplify アプリ                       ├ Amplify アプリ
  └ Harness 実行ロール                   └ Harness 実行ロール
 案件スタック × 2                       案件スタック × 1
  ├ 案件1（Harness / グループ / ブランチ） └ 案件3
  └ 案件2
```

**コードは変わらない。** `instance` を企業ごとに変えるだけ。
別の `instance` で独立した土台が立つことは 2026-08-12 に実測済み
（`fdedemo0809` と `fdedemo0812`）。

**分離は 2 段になる。**

| 段 | 何が分かれるか |
|---|---|
| 企業 | **Cognito User Pool ごと。** 企業 A の担当者は B 社のデモに**そもそもログインできない** |
| 案件 | 同じ User Pool 内で**グループ**。Harness が `cognito:groups` を `CONTAINS` で検証 |

案件をまたぐ分離が効くことは 2026-08-09 に実測済み（グループを外したトークンは弾かれる）。

## 3.3 企業リポジトリの作り方

**GitHub のテンプレートリポジトリ機能を使う。**

```bash
gh repo create fde-demo-<企業> --private --template <土台リポジトリ>
```

`git clone` ではなく `--template` にする理由は **履歴が入らない**こと。
土台リポジトリの開発履歴（検証用の架空案件を含む）を持ち込まない。

**`--private` を必ず付ける**（CLAUDE.md）。

作った直後に**見本の案件を消して**、その企業の案件を作る。手順は `RUNBOOK.md` に書く。

## 3.4 `demos/` の 3 件は見本として残す

`smoke` / `sales` / `hr` は検証用に作った架空の案件だが、**型ごとの見本として価値がある**。

| | 型 | 見本としての価値 |
|---|---|---|
| `smoke` | 土台検証用 | 最小構成。ツール 1 つ |
| `sales` | データ分析型 | Code Interpreter、傾向の仕込み方、機会損失額の出し方 |
| `hr` | ナレッジ判断型 | ツール 2 つ、`escalated` による拒否、回付先の示し方 |

要件書 4.3 は「近い既存案件を**見本として参照**する（テンプレート化しない）」と定めている。
**土台リポジトリに残し、企業リポジトリでは消す。**

# 4. 実装として要るもの

**コードの変更はない。ドキュメントだけ。**

| ファイル | 何を書くか |
|---|---|
| `docs/REQUIREMENTS.md` 7.1 | 決着済みとして、決めたことと理由を書く |

| `RUNBOOK.md` | 「企業リポジトリを作る」章を足す。**実行して確かめてから書く** |
| `CLAUDE.md` | 現状の記述に、企業ごとに分ける方針を反映 |
| `demos/index.ts` | 3 件が**見本**であることをコメントに書く |

# 5. 未確認のこと

**推測で埋めていない。**

| | 何が分からないか | いつ潰すか |
|---|---|---|
| 1 | `gh repo create --template` が、**`.claude/` や `docs/` を含めて期待どおりコピーするか**。テンプレート機能はデフォルトブランチのファイルをコピーするが、隠しディレクトリの扱いを実測していない | `RUNBOOK.md` を書くとき |
| 2 | 土台リポジトリを **GitHub の template として設定する手順**（リポジトリ設定の変更が要る）。そもそもこのリポジトリにリモートが無い | 同上 |

**2 は今すぐには潰せない。** このリポジトリにはリモートが設定されておらず、
GitHub 上に存在しない。**`RUNBOOK.md` にはその旨を明記し、
実行して確かめていない手順を確認済みとして書かない。**

# 6. この設計の範囲外

| | 理由 |
|---|---|
| 土台の修正を既存の企業リポジトリへ配る仕組み | **作らないと決めた**（2.2）。必要になったらその企業で直すか作り直す |
| 企業をまたぐ横断的な管理（一覧、棚卸し） | 案件が 1 日 1 件程度の規模では要らない。`cleanup-check` が AWS 側を見る |
| 実データの取り込み・VPC・本番品質 | 要件書 6 章のスコープ外 |
