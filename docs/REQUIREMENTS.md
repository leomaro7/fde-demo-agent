# FDE デモ基盤 — 要件書

作成日: 2026-08-07

このドキュメントは、別セッションでゼロから作り直すための入力です。
**実測で確定した事実**と、**失敗から導いた設計原則**を引き継ぎます。

---

# 1. 何を作るか

クライアントとの打ち合わせで聞いた課題を、**同日中に触れるプロトタイプ**として
提示するための基盤。

```
打ち合わせメモ  →  設定を書く  →  数分  →  認証付きの URL
```

目的はクライアントに導入後のイメージを持ってもらうこと。動作の網羅性や
本番品質は目標ではない。判断に迷ったら「クライアントがイメージを持てるか」を
基準にし、「正しく動くか」を基準にしない。

## 1.1 達成済みの水準

| 指標 | 実績 |
|---|---|
| 設定を書いてから URL 発行まで | 217〜256 秒 |
| 土台の構築（CDK） | 50 秒 |
| 土台の撤去 | 33 秒・残骸ゼロ |
| 実案件で検証した型 | 3 種類 |

# 2. なぜ作り直すのか

**機能は動いた。作り方が悪かった。**

3 件のデモはいずれも成功し、うち 1 件は仕込んだ傾向（郊外店の失速）を
エージェントが自力で発見して機会損失額まで算出した。基盤としては成立している。

問題は次の点にある。

## 2.1 設計判断の誤りを実装後に直し続けた

| 誤った判断 | 発覚の経緯 | 手戻り |
|---|---|---|
| IaC を使わず SDK スクリプトで構築 | 「CDK のほうがいいのでは」と指摘を受けて | 全面移行。3 ファイル・テスト 7 件を破棄 |
| IAM ポリシーを `/tmp` に書く手順 | 「本当に作成されますか」と指摘を受けて | `infra/` へ移動 |
| IAM ロール名を固定 | 「同名が存在したら作成できないのでは」 | 冪等化コードを書いた翌日、CDK 移行で**そのコードごと不要に** |
| Cognito ドメイン・Amplify アプリ名を固定 | 「2 個目を同じアカウントで作れないのでは」 | `instance` による分離を追加 |
| ドメインにアカウント ID を含める | 「`${this.account}` はいらない」 | 削除（ログイン URL に露出していた） |
| Amplify サービスロールを画面で作る想定 | 「CDK で作るのでは」 | スタックに追加 |

**いずれも実装前に判断できたはずのもの。** 特に IaC の不採用は、
「リソースが少ない」という**実態と食い違う前提**に基づいていた。

## 2.2 ドキュメントを検証せずに書いた

README を書いたあと、通し検証で次が見つかった。

- `/tmp` にポリシーを書く手順（一時ファイルが残る・Git で追跡できない）
- Amplify の接続手順が**実際の画面遷移と違う**（新規作成時の画面を書いていた）
- Transaction Search が「実行不要」としか書かれておらず、**確認方法がない**
- テスト件数が 2 箇所とも古い（45 件 → 実際 72 件）
- `gh repo create` が 2 周目で失敗する分岐がない

**実行して確かめていない手順を書いた**のが原因。

## 2.3 ルールがなかった

`CLAUDE.md` も `.claude/settings.json` もない状態で進めたため、
判断がその場限りになった。上記の誤りの多くは、**最初にルールがあれば防げた**。

# 3. 引き継ぐ資産

作り直しでも**再調査不要**な、実測で確定した事実。

## 3.1 / 3.2 実測で確定した AWS 仕様

**`.claude/skills/aws-fact-check/references/aws-facts.md` に移した。**

AgentCore Harness・Cognito・Amplify の実測値、および event stream の
フレーム構造はそちらにある。AWS を触るときだけ読み込まれればよい情報なので、
`aws-fact-check` スキルの参照ファイルに置いている。

新しく確定した仕様もそちらに追記する。

## 3.3 デモの型（実案件 3 件から）

| 型 | 特徴 | 可変点 |
|---|---|---|
| 検索・照合型 | データを引いて条件に当てはめる | seed + 単純な filter |
| ナレッジ判断型 | 根拠を示し、判断できないものを切り分ける | seed 2 種 + 判断基準をプロンプトに |
| データ分析型 | 集計して傾向を出す。Code Interpreter を使う | seed（全件返す）+ 分析指示 |

**3 件とも `tools.ts` はほぼ同一**（`keyword` で filter して返すだけ）。
差が出るのは `system_prompt` と `seed` の中身。

## 3.4 デモの質を決める要素（最重要）

**説得力を決めたのは、エージェントが答えを拒む場面だった。**

| 案件 | 拒む条件 | 効果 |
|---|---|---|
| 事務ナレッジ | 規程にない個別事情、承認が必須の事項 | 「二次エスカレーションが必要です」と宛先まで示した |
| 売上分析 | データに含まれない原因 | 「データからは分かりませんが」と前置きし調査項目を提示した |

運用部門ほど「何でも答える AI」を警戒する。**そしてこの情報は打ち合わせメモに
絶対に書かれない**。クライアントは「できるようになりたいこと」を話し、
「できてはいけないこと」は話さないため。

したがって案件を作るときは **「このデモで答えてはいけないことは何か」を必ず聞く**。

## 3.5 seed に傾向を仕込む

売上分析の案件では「郊外店だけ下期に前年比 89%」を意図的に埋め込み、
エージェントが自力で発見して機会損失 6,938 万円まで算出した。これがデモの山場になった。

**データが平坦だと発見がなく、デモが単調になる。**

# 4. 機能要件

**この章は「何が必要か」だけを書く。** どう実現するかは設計で決める（7.0）。
前身での実装は参考として併記するが、**そのとおりに作る義務はない**。

## 4.1 土台（一度きり構築）

### 要件

| | 内容 |
|---|---|
| エージェント | クライアントの業務に沿った応答をし、**何を調べたかが利用者に見える**こと |
| 認証 | 案件ごとに独立したアカウントで、他案件の画面に入れないこと |
| 配信 | 案件ごとに固有 URL。ブラウザだけで触れること |
| 撤去 | **1 手で残骸なく消える**こと。課金対象を残さない |
| 並走 | 数件が同時に動き、数週間保持できること |

**実行トレースが見えることはこの基盤の差別化点。** 単に答えるだけの
チャットとの差はここに出る。

### 前身での実装（参考）

- AgentCore Harness（設定のみ・コンテナ不要）+ Cognito + Amplify Hosting
- 画面は左に会話、右にトレース
- Code Interpreter の入力には生成コードとデータ全体が入るため、そのまま出すと
  画面が JSON で埋まった。**コード本体だけを抜き出し、長さも抑える**必要がある

## 4.2 案件ごと

### 要件

案件ごとに変わるのは、**エージェントへの指示・ダミーデータ・見た目**の 3 種類だけ。
それ以外は土台が担う。

指示には必ず次の 3 点を含める。

1. **調べる順序** — どのツールをどの順で呼ぶか
2. **根拠の示し方** — 条番号、事例番号、計算に使った数字
3. **答えてはいけない条件** — 該当時に何と言い、どこに回すかまで

商談で見せる質問を 3 つ用意し、**3 つ目に「答えられない質問」を置く**。
商談ではこれを最初に見せると、運用部門の懸念を先に否定できる。

ダミーデータには**発見できる傾向**を仕込む（3.5）。

### 前身での実装（参考）

`demos/<slug>/` に `demo.yaml`（指示・ツール宣言・入力例）、`brand.yaml`（色）、
`seed/`（JSON）、`tools.ts`（検索処理）の 4 点を置いた。

**この 4 点構成は前身の自作スキーマであり、要件ではない。** `AWS::BedrockAgentCore::Harness`
や AgentCore CLI の設定ファイルで代替できる可能性がある（7.0）。

**2026-08-08 追記** — 自作スキーマを続ける（7.0）。ただし **3 点**に減らし、
YAML ではなく **TypeScript** で書く。CDK とフロントが同じファイルを import でき、
パーサと検証が両側から消えるため。

## 4.3 生成（工場）

### 要件

打ち合わせメモから案件を起こす手順があること。**型が見えるまでは自動生成しない**
（9 章）。

- **必ず聞くのは 2 項目だけ**（答えてはいけない条件／クライアント名）。
  それ以外はメモから推測する
- 近い既存案件を**見本として参照**する（テンプレート化しない）
- 作ったものを**検証**してから見せる
- **承認は 1 回だけ**。その後は止めない

### 現状

`.claude/skills/new-demo` が骨子を決めるところまでを担う。生成とデプロイは
7.0 の決着後に足す。

# 5. 設計原則（今回の失敗から）

作り直しでは**最初から**これを守る。

## 5.1 インフラは IaC で書く

**例外なく CDK（または CFn）で書く。** 「リソースが少ないから」は理由にならない。
今回それで判断を誤り、冪等性・削除順序・命名衝突をすべて自前で実装する羽目になった。

前身は**案件ごとのリソースだけ SDK スクリプト**にした。CFn が削除完了を待つ分だけ
遅くなるという理由だった。

**2026-08-08 追記** — 分担は**決着した**。**案件も CDK で書く**（7.0）。
土台スタック 1 つと案件スタック 1 つずつに分け、案件の撤去は `cdk destroy` 1 手。

**例外が 1 つある。** デモ用ユーザーの作成は CFn に載せない。
`AWS::Cognito::UserPoolUser` に一時パスワードを置く手段が無く、置けたとしても
テンプレートに平文が残るため。手順書側の CLI コマンドにする。

## 5.2 グローバルに一意な名前は必ず可変にする

| 対象 | 理由 |
|---|---|
| Cognito ドメインプレフィックス | リージョン内で全アカウント共通の名前空間 |
| IAM ロール名 | アカウント内で一意。**そもそも固定しない**（IaC の自動命名に任せる） |
| Amplify アプリ名 | 重複すると運用時に見分けがつかない |
| CFn スタック名 | 同一アカウントに複数の環境を置けなくなる |

同一アカウントに複数の土台（dev/prod、企業ごと）を置けることを**最初から前提**にする。

## 5.3 アカウント ID を利用者に見せない

Cognito のログイン URL はクライアントのブラウザに表示される。
機密ではないが、晒す理由もない。

## 5.4 アカウント全体の設定はスタックに含めない

Transaction Search のような**アカウント・リージョン単位のグローバル設定**を
プロジェクトのスタックが所有すると、スタック削除で他プロジェクトに影響する。

## 5.5 一時ファイルを使わない

設定ファイル（IAM ポリシーなど）は**リポジトリに置く**。
`/tmp` に書く手順は、追跡できず・残り続け・環境によっては書けない。

## 5.6 手順書は実行してから書く

**実行していない手順を書かない。** 今回、Amplify の接続手順を画面を見ずに書き、
実際の遷移と違っていた。

- コマンドは実際に流す
- コンソール操作は実際に画面を見る（できなければ「未確認」と明記する）
- 「既に〜なら不要」と書くときは、**確認するコマンドを先に示す**
- 2 周目（既にリソースがある状態）で成立するかを確認する

## 5.7 ドキュメントに数値を埋め込まない

テスト件数のような変動する数字は書かない。今回 2 箇所で古くなり、
片方だけ直して不整合が起きた。

## 5.8 削除は不可逆と扱う

削除前に対象を明示し、承認を得る。撤去手順は**実際に実行して検証**する。

# 6. 非機能要件・制約

| | |
|---|---|
| リージョン | ap-northeast-1（AgentCore 利用可を確認済み） |
| データ | **ダミーのみ**。実データの取り込み経路は作らない。NDA とセキュリティ審査を待たずに着手できることが当日提示の前提 |
| VPC | **構築しない**。ファイルマウントを使わないことで回避する |
| ダミーデータとツール実装 | **フロント側に置く**。AWS 側に保存しない（クライアントへの説明材料にもなる） |
| リポジトリ | private。案件ごとのブランチにクライアント固有の情報が入る |
| 本番品質 | 目指さない。可用性・負荷対策・監査ログは対象外 |

## 6.1 土台に乗らない要望

打ち合わせの場で判断できるよう明示する。

| 要望 | 可否 |
|---|---|
| 社内文書に答える / 業務データを調べて提案する | 設定を埋めるだけ |
| データを分析してグラフを見せる | Code Interpreter を有効にするだけ |
| 承認フローを挟む、条件で分岐する | ツールを少し書く |
| 音声対話、帳票画像の読み取り | **当日は不可** |
| 既存業務画面への埋め込み | **当日は不可** |

# 7. 未解決の論点

作り直しの設計時に判断する。

## 7.0 そもそも何を自作するのか（2026-08-07 追加）

> **決着済み（2026-08-08）** —
> [docs/superpowers/specs/2026-08-08-what-to-build-design.md](superpowers/specs/2026-08-08-what-to-build-design.md)
> に設計がある。判断の理由は `DECISIONS.md`。
>
> | 論点 | 決めたこと |
> |---|---|
> | 案件リソースを何で作るか | **自前 CDK + `CfnResource`。`@aws/agentcore-cdk`（alpha）に依存しない** |
> | ツールをどこで実行するか | **ブラウザ側**（`inline_function`）。**Code Interpreter だけ Harness 側** |
> | 設定ファイルの形式 | **自作スキーマ。TypeScript** |
>
> **下に書かれた「前提が崩れた」という見立ては、半分外れた。**
> `@aws-sdk/client-bedrock-agentcore` は **SigV4 しか話せない**ため、
> JWT で案件を分離する限り event stream デコーダは自作が必然だった。
> エージェント層は前身とほぼ同じ大きさになる。**消えるのは案件構築の
> SDK スクリプトのほう**で、これが CDK に置き換わる。
>
> **以下は決着前の記述。判断の経緯として残す。**

**7.1 / 7.2 より先に、これを決める。** この 2 つは「自作する」前提で書かれているが、
その前提が確認で崩れた。

公式ドキュメントで確認した事実。

| | 内容 |
|---|---|
| CloudFormation リソース | **`AWS::BedrockAgentCore::Harness` が存在する。** `Model` / `SystemPrompt` / `Tools` / `Memory` / `AuthorizerConfiguration` / `Skills` などプロパティ一式が揃っている |
| AgentCore CLI | `npm install -g @aws/agentcore`。`create` / `deploy` / `dev` / `invoke` / `status`。設定は `agentcore/agentcore.json` |
| CLI の実装 | **内部で `@aws/agentcore-cdk` の CDK コンストラクトを使っている**（ドキュメント記載） |
| Harness の位置づけ | 「declare the agent in a config file（model, prompt, tools, memory）and AgentCore runs the loop for you. **No framework, no orchestration code**」 |
| ツール実行 | 「the harness handles orchestration, **tool execution**, memory management, and response generation」 |

**これが崩す前提。**

1. **「土台は CDK、案件は SDK スクリプト」という分担** — 案件も CFn / CDK で書ける。
   公式コンストラクトがあるなら、手書きの SDK スクリプトを保守する理由が薄い
2. **エージェント層を自作する必要があるか** — 前身は `inline_function`
   （return-of-control）を選んだため、**ツールをブラウザ側で実行する必要があり**
   ツールループの実装が要った。ブラウザから直接叩く構成にしたため
   event stream のデコーダも要った。Harness にツールを任せる構成なら、
   どちらも不要になりうる
3. **案件の設定ファイルの形式（4.2）** — 前身の 4 点構成は自作スキーマ。
   `agentcore.json` や CFn テンプレートで代替できるなら、この形は要らない

**決めること。**

- 案件リソースを CFn / CDK / AgentCore CLI のどれで作るか
- ツールをどこで実行するか（Harness 側 / ブラウザ側）。これがエージェント層を
  自作するかどうかを決める
- 案件の設定ファイルを自作スキーマにするか、公式の形に寄せるか

**確認していないこと。** `@aws/agentcore-cdk` が Harness を扱えるか（Runtime 専用の
可能性がある）、AgentCore CLI が Harness の作成に対応しているか、Harness 側でツールを
実行させたときにブラウザへどう返るか。**設計前に `aws-fact-check` で確かめること。**

## 7.1 リポジトリと Cognito の分割単位

現行は「1 リポジトリ・1 User Pool・案件ごとにブランチとグループ」。
これに対し、**企業ごとに分ける**案がある。

```
A 社リポ（User Pool を社内で共有、グループで検証）
  ├ 案件 1  ├ 案件 2  └ 案件 3
B 社リポ（同上）
```

| 分割を後押しする事実 | 現行を後押しする事実 |
|---|---|
| クライアントにソースを渡す場合、他社の案件が入ったリポジトリは渡せない | 土台の修正が全案件に一度で効く（実際、3 件目で見つけた欠陥の修正は main へのマージだけで済んだ） |
| ブランチを削除しても Git 履歴は残る。完全消去にはリポジトリごと削除するしかない | Amplify は 1 アプリ = 1 リポジトリのため、企業ごとに初期設定が要る |
| User Pool の作成は**数秒**で終わる（「時間がかかる」は誤った前提だった） | |

**分割する場合の設計課題**: 土台をコピーせず共有する方法
（npm パッケージ化、テンプレートリポジトリ + subtree など）。

なお「別案件のアカウントで開ける」問題は、**開発者がプライベートウィンドウを
使えば回避できる**ため、それ単独では分割の理由にならない
（クライアントは 1 社 1 アカウントしか持たない）。

## 7.2 案件ごとのリソースを IaC にするか

現行は速度を理由に SDK スクリプト。`AWS::BedrockAgentCore::Harness` は
存在するので技術的には可能。案件数が増えて管理が問題になったら再検討する。

**2026-08-07 追記** — 7.0 に統合された。「速度を理由に SDK スクリプト」という判断は、
公式の CDK コンストラクトと CLI の存在を知らずに下したもの。判断材料が変わっている。

**2026-08-08 追記** — **IaC にする**（7.0 で決着）。ただし
**CFn 経由の案件デプロイ所要時間は未実測**であり、`217〜256 秒` から大幅に悪化するなら
この判断は覆りうる。設計書 5 章の未確認 4 がそれ。

# 9. 進め方の推奨

今回の反省を踏まえた順序。

1. **ハーネスを先に用意する**（8 章）。ルールがない状態で進めない
2. **土台を IaC で作る**。スクリプトから始めて移行、という遠回りをしない
3. **実案件を 1 件通す**。ここで土台の欠陥が出る（今回 2 件目・3 件目で発覚した）
4. **手順書を書きながら実行する**。書いてから検証すると今回のように多数の欠陥が出る
5. **工場（生成スキル）は型が見えてから**。今回この判断は正しかった

## 9.1 やらないほうがよいこと

- ドキュメントを先に書いて後で検証する
