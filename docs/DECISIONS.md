# 設計判断の記録

**なぜそう決めたかを時系列で残す。** 前身のプロジェクトでは判断の根拠が設計書に
散在し、後から「なぜこうなっているのか」を追えなくなった。

新しい判断をしたら**上に**追記する。書くのは次の 4 点。

- **日付**
- **決めたこと**
- **なぜ** — 何を避けたかったのか
- **代わりに何を捨てたか** — トレードオフを明示する。後で覆すときの材料になる

## 覆した判断の扱い

**消さない。** 「何を試して、なぜ戻したか」は次の判断の材料になる。

代わりに、覆したエントリの冒頭に **> 失効** の 1 行を入れ、どのエントリで
覆したかを書く。**引用ブロックが付いているものは現状ではない。**

上から新しい順に並ぶが、日付だけでは前後が分からないことがある（同日に何度も
判断が変わることがある）。**引用ブロックの有無で生死を見ること。**

## 2026-08-13 リポジトリをクライアント企業ごとに分ける（7.1 決着）

**決めたこと** — 詳細は
[docs/superpowers/specs/2026-08-13-repo-split-design.md](superpowers/specs/2026-08-13-repo-split-design.md)。

| 論点 | 決めたこと |
|---|---|
| リポジトリの分割単位 | クライアント企業ごと |
| Cognito User Pool | 企業ごと（`instance` を変えるだけ。コードの変更は不要） |
| 案件の管理単位 | 同一リポジトリ内の `demos/<slug>/`。Git のブランチは使わない |
| 土台の共有 | **仕組みを作らない** |
| 引き渡す範囲 | 案件部分だけ。土台は当社の資産として保持 |

**なぜ** — 分割の理由が 1 つに絞られていた。

7.1 が挙げていた 3 つのうち、「配信物に他社データが混ざる」は 2026-08-12 に
技術的に解決し（`vite.config.ts` が `VITE_DEMO_SLUG` から案件を別名解決する）、
「完全消去には Git 履歴ごと消すしかない」は分割の帰結として解決する。
残るのは **他社の案件が入ったリポジトリは渡せない**だけ。

同時に、現行を後押ししていた「Amplify は 1 アプリ = 1 リポジトリ」も消えた。
リポジトリを接続しないと決めたため（設計書 2026-08-08 の 4.1）、
企業ごとの初期設定という負担は発生しない。

**土台を共有する仕組みは作らない。** 7.1 は npm パッケージ化や subtree を
設計課題として挙げていたが、**作らないと決めた**。デモは数週間で廃棄する前提であり、
土台の修正は次に作る企業リポジトリから効けば足りる。既存の企業リポジトリで
直す必要が出たら、その場で直すか作り直す。

**捨てたもの** — **土台の修正が全案件に一度で効くこと。**

2026-08-12 にこの利点が実際に効いた。案件 3 件目で見つけた「配信物に他案件が
混ざる」欠陥の修正が、`main` へのマージだけで全案件に及んだ。**分割後はこれが
効かない。** 同じ欠陥を別の企業リポジトリでも踏む。失うものは軽くないが、
配る仕組みを持つコストのほうが、速度を目的とするこの基盤には重い。

**覆りうる条件** — 企業が 5 社を超え、同じ欠陥を 3 回以上別リポジトリで踏んだら、
共有の仕組み（npm パッケージ化）を再検討する。**回数を数えること。**

**未確認** — `gh repo create --template` が `.claude/` や `docs/` を含めて
期待どおりコピーするかは実測していない。このリポジトリにリモートが無く、
GitHub 上に存在しないため実行できない。`RUNBOOK.md` にその旨を明記した。

## 2026-08-12 ビルド設定をシェルの環境変数から切り離した

**決めたこと** — `web/vite.config.ts` が `web/.env.local` を自分で読み、
`define` で値を埋め込む。**Vite の環境変数の仕組みに任せない。**
必須キーが欠けていればビルドを失敗させる。

**なぜ** — **実際に事故が起きた。**

Vite は `.env` ファイルに加えて `process.env` の `VITE_*` も取り込み、
**そちらを優先する。** 開発者のシェルに前身プロジェクトの環境変数が 5 つ残っており、
`web/.env.local` が無視されて、**前身の Cognito ドメインが焼き込まれた状態で
デプロイされていた。** 画面は「設定が足りません」で止まった。

止まったのは運がよかっただけである。`VITE_HARNESS_ARN` がたまたま欠けていたから
気づけたが、5 つ揃っていれば**別のクライアントの Harness を指したまま
商談に持っていける。** この基盤にとって最も避けたい事故がこれである。

`App.tsx` の読み方も直した。`readConfig(import.meta.env)` とオブジェクトごと渡すと
Vite の静的置換が効かない。1 つずつリテラルで参照する形にした。

**捨てたもの** — Vite の標準的な env の使い方から外れる。`.env.production` などの
モード別ファイルは効かなくなる。案件ごとに 1 つの設定しか要らないので許容する。

**見つけ方** — ブラウザで実際に開いて初めて分かった。テストは全部緑だった。
**通し確認を省いていたら商談で踏んでいた。**

## 2026-08-08 「アカウント ID を見せない」の検査範囲を利用者に見える名前に限った

**決めたこと** — 土台スタックのテストから、合成テンプレート**全文**にアカウント ID が
現れないことを確かめるアサーションを外した。Cognito ドメインと Amplify アプリ名の
厳密一致は残す（値が違えばそこで落ちる）。

**なぜ** — **原理的に成立しない検査だった。**

実行ロールの信頼ポリシーは、混乱した代理問題を防ぐために `aws:SourceAccount` で
アカウントを絞る。この値はテンプレートにリテラルで残る。同じテストファイルの中で
「全文にアカウント ID が無いこと」と「信頼ポリシーがアカウント ID で絞られていること」を
同時に要求していた。

5.3 が守ろうとしているのは**利用者に見える名前**である。理由は
「Cognito のログイン URL がクライアントのブラウザに表示されるから」であり、
対象は Cognito ドメインプレフィックスと Amplify アプリ名。IAM ポリシーの中身は
クライアントの目に触れないうえ、アカウントで絞ることはむしろ正しい。

**捨てたもの** — 「どこにもアカウント ID が出ない」という広い保証。
今後アカウント ID を含む名前を新しく足しても、テストは自動では気づかない。
対象を増やすときは、その名前ごとに厳密一致のアサーションを足すこと。

**この検査を書いたのは実装計画のほう**なので、計画側も同時に直した。
矛盾したテストをそのまま残すと、次に同じ計画を読む人がまた同じところで止まる。

## 2026-08-08 要件書 7.0 を決着させた — エージェント層は自作する

**決めたこと** — 3 点。詳細は
[docs/superpowers/specs/2026-08-08-what-to-build-design.md](superpowers/specs/2026-08-08-what-to-build-design.md)。

| 論点 | 決めたこと |
|---|---|
| 案件リソースを何で作るか | 自前 CDK + `aws-cdk-lib` の `CfnHarness`（L1）。`@aws/agentcore-cdk` に依存しない |
| ツールをどこで実行するか | ブラウザ側（`inline_function`）。Code Interpreter だけ Harness 側 |
| 設定ファイルの形式 | 自作スキーマ。TypeScript |

**なぜ** — **7.0 の期待は成立しなかった。**

7.0 は「Harness にツールを任せれば、ツールループも event stream デコーダも
不要になりうる」と疑っていた。実際に確かめたところ、
**`@aws-sdk/client-bedrock-agentcore` の認証スキームは `aws.auth#sigv4` だけ**で、
`smithy.api#httpBearerAuth` が無い。Harness を `customJWTAuthorizer` で保護する限り
SDK は使えず、`fetch` + 自作デコーダになる。

逃げ道は 2 つあったが、どちらも取らなかった。`httpAuthSchemes` への差し込みは
`@internal` 印の設定で版が上がると壊れる。authorizer を IAM にすると
**`cognito:groups` による案件分離が使えなくなり**、要件書 4.1「他案件の画面に
入れない」に直接刺さる。

**前身の「ブラウザ直叩き + 自作デコーダ」は思いつきではなく、
JWT で案件を分離するという要件からの必然だった。** 7.0 はこれを
「`inline_function` を選んだ帰結でしかない」と読んだが、順序が逆だった。

公式コンストラクトを使わないのは別の理由による。`@aws/agentcore-cdk` は
**`0.1.0-alpha.46`** であり、しかも `AgentCoreHarness` は
**`harnessDir`（`harness.json` を置くディレクトリ）を必須**にしている。
CLAUDE.md「構造を前提にする仕組みは、それが決まってから作る」に正面から反する。
中身は生の `CfnResource` なので、依存せずに**プロパティ名の正解だけ読める**。

**2026-08-09 訂正** — 「L1 が無い」は `@aws/agentcore-cdk` のソースコメントを信じたもので、
**誤り**。`aws-cdk-lib@2.263.0` に `CfnHarness` がある。実装は L1 に移した。
ただし **L1 が守るのは名前と構造だけで、列挙値は素の `string`**。
実際 `InboundTokenClaimValueType` に存在しない `STRING_LIST` を書いており、
それを拾ったのはコンパイラではなく `cdk synth` の CloudFormation スキーマ検証だった。

**捨てたもの** — 3 つ。

- **`@aws/agentcore-cdk` がタダでくれる検証**（`harnessName` 40 文字など）と
  実行ロールの権限セット。自分で書く
- **公式が仕様変更に追随してくれること。** CFn のプロパティ名が変われば自分で直す
- **IaC の完全性。** デモ用ユーザーの作成だけ CFn に載せられない
  （一時パスワードをテンプレートに置く手段が無い）。5.1 の明示的な例外とし、
  手順書側の CLI コマンドにする。**手段が本当に無いかは未確認**

**覆りうる条件** — 設計書 5 章に未確認を 5 件残した。とくに
**CFn 経由の案件デプロイ所要時間**が `217〜256 秒` から大幅に悪化するなら、
「案件だけ SDK スクリプト」という前身の分担が再浮上する。
そのときはこのエントリを失効させて理由を書く。

## 2026-08-07 認証情報を返す読み取りコマンドを deny に追加した

**決めたこと** — `deny` に次を追加。

- `aws sts get-session-token` / `get-federation-token` — 一時的なシークレット
  アクセスキーが返る
- `aws ecr get-login-password` — レジストリのパスワードが返る
- `cat .env` / `cat .env*`

**なぜ** — `allow` の `Bash(aws * get-*:*)` は読み取り系のつもりで書いたが、
**AWS の `get-*` には認証情報を発行するものがある**。無確認で通ると、
値がそのまま会話に残る。`secretsmanager` と `ssm` だけ塞いで満足していた。

`.env` は `Read(./.env)` で塞いだつもりだったが、`cat` は Claude Code の
**組み込み読み取りコマンドとして無条件で実行される**ため、Read ツールの deny を
迂回する。

**限界** — `head` / `tail` / `grep` など、ファイルを読める手段は他にもある。
**列挙で塞ぎ切ることはできない。** `.env` を `.gitignore` に入れてあることと、
そもそも読む必要がないことのほうが本質的な防御である。

**捨てたもの** — 一時認証情報を使う正当な作業（フェデレーション、ECR への
push）があれば都度確認になる。このプロジェクトではどちらも使わない。

## 2026-08-07 レビュー結果を反映してハーネスを組み直した

> **一部失効** — フックに関する 3 項目（`validate-demo` を exit 2 に、引き金を
> `demo.yaml` に絞る、`pre-commit-gate` を `.md` で飛ばす）は、その後フックごと
> 削除された。「フックを 1 つに減らし、許可リストから npm 依存を外した」を見ること。
> 権限・`cleanup-check`・`verify-runbook`・`aws-fact-check` の変更は現在も有効。

外部レビュー 2 本（ドキュメント検査／全体の批判的レビュー）を受けた結果。
主な変更と、その理由。

**ask から `aws * create-*` / `update-*` / `put-*` を外した** — `ask` は `allow` より
優先する（公式ドキュメント: "a matching ask rule prompts even when a more specific
allow rule also matches the same call"）。そのため、このハーネスが最も推している
`--generate-cli-skeleton` が毎回止まっていた。しかも本当にリソースを作る経路は
`npm run deploy` の SDK 呼び出しで、`aws` CLI を 1 回も通らない。**摩擦の位置が
反転していた。** 破壊的操作の境界は `npm run deploy` / `destroy` 側で押さえる。
`delete-*` だけは残した（skeleton が止まるのは許容。実削除を止める価値のほうが大きい）。

**deny を追加した** — `aws * get-*` の allow で `secretsmanager get-secret-value` と
`ssm get-parameter --with-decryption` が無確認で通り、平文がトランスクリプトに残る
状態だった。`.env` の読み取りも塞いだ。

**`validate-demo` を exit 2 にした** — exit 0 のフックの stderr は debug log にしか
出ず、Claude にも人にも届かない。**検証が失敗しても誰も気づかない状態**だった。
「フックが守ってくれている」という誤った安心だけが残るので、検査が無いより悪い。

**`validate-demo` の引き金を `demo.yaml` だけに絞った** — 案件は 5〜6 ファイルあり、
全ファイルで発火させると最後の 1 つが書かれるまで必ず失敗する。exit 2 にした今、
失敗通知が続けば「無視してよい通知」として学習され、検査が形骸化する。

**`pre-commit-gate` を `.md` だけのコミットで飛ばすようにした** — 前身のコミット
20 件のうち 9 件が `docs:` / `chore:` だった。

**`cleanup-check` の管理外判定を直した** — CFn タグの有無で判定していたが、
このプロジェクトは「案件は SDK スクリプト」なので**案件リソースは設計上タグを持たない**。
全部が「管理外」に出て報告が使い物にならなかった。加えて `FdeDemo` という prefix を
